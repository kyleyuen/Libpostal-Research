## 5. What worked (in order) and the lessons

- **Precompute from the model at load; look up at parse.** This is the biggest family of wins:
  - 056: first-token table;
  - 101: prefix/suffix NULL flags in spare FTT bits (+1.7% / +3.1%);
  - **119: component-phrase feature ids** for all 4.01M trie keys, with a length guard proving runtime string == key (+2.7% v1, **+5.6% OSM**, +4.7% unseen). It is the only recent change that helps OSM most.

  It works because it removes *compute* (string building, hashing, compares) and dependent misses together.
- **A prefetch only wins when issued a whole stage before a serialized use, from data already in hand** (074, 077, 114). Prefetching every line of transition rows only (114) helped golden-v1 and was neutral on OSM. All-rows variants (085, 113) lost on OSM.
- **Exact algorithmic compute cuts** help OSM-style data most: 091 max-only Viterbi, 098 paired normalization.
- **Golden-v1 (Senzing-derived, long addresses) rewards memory-side tricks; OSM-style data does not.** Screen both every time, then unseen. At least five candidates died this way (079, 085, 113, 126, partly 114).

## 6. What does NOT work (don't retry without a genuinely new angle)

**Memory-side, within an address:**
- 004, 012 iC, 027, 037, 046 (various prefetch / interleave);
- 075 vocabulary-arena prefetch;
- 078 eager memo; 081 push-time prefetch; 084 early postal prefetch;
- 085/113 all-row prefetch;
- 105 postcode fall-off flags (those walks are near-root and cached);
- 111/126 postcode digit tables (126: golden-v1 only);
- 128 row-mask clearing (memset already at store bandwidth).

**Model restructuring (exact):**
- 135: lossless weight compression is impossible (the weights are essentially unique doubles).
- 137: a hot tier of the most frequent words' rows (4 MB, model-ranked) covers about 88% of transition records but is slower: hot rows already stay cached, and the routing costs compute.
- 063: a separate cold table adds a miss.
- 087: dense rows.
- 130: dictionary-phrase ids are exact but too small (about 2 keys/address, +1.1% / −0.2%).

**Compute:**
- 097 unrolled accumulation; 070 `-mcpu=native` / -O3; 018 tokenizer -O2;
- 071 certified early exit: label margins are 20–60× smaller than sound bounds;
- 099/133 phrase join with known lengths: real, but +0.5–0.9%, under the threshold;
- 122/131 bigram integer keys: canonicalizing bigram parts costs more than the lookup saves; only 37–39% of bigram parts are already cached (kill rule 60%).

**Cross-address (single thread, exact):**
- 138: lookahead prefetch of the next address's predictable data is slower (−3…−7%). That data is already cached; predicting it costs compute.
- 139/140: full interleaving with coroutines, per-address state swap and a batch API is exact in every mode, including random-switch stress and 2 × 2M fuzz, but **slower in every configuration (−3…−10%)**, even with one switch per address. The hardware itself overlaps 8 independent chains (139: 3.95× with 4 coroutines on a pure chase). The parser lacks enough long independent waits, and interleaving makes L1 working sets compete.
- 140's runtime is complete and reusable (`experiments/140-interleave-runtime/tools/runtime_140.c`, `patch_140.py`) if a future idea needs a batch API.

**Platform:** superpages are unavailable on macOS arm64 (041). Parallel timing distorts results.

## 7. Ceilings (what physics allows under these rules)

- **Warm bound** (all data cached, compute only): ≈ 2.47 µs development, ≈ 2.2 µs OSM, so roughly 12× golden-v1 and 8.6× OSM. Harness-mixed estimates; 088 measured 11.1× / 8.1× / 7.7× unseen on the older pcp build.
- **7.8× on OSM** needs 2.48 µs, which is within about 12% of pure compute. Memory-side work alone cannot get there; compute must shrink too.
- **035 realistic ceiling** (feature keys replayed, lookups still done): 8.7× golden-v1, 7.6× OSM, on an old build.
- **Rule changes that would move the ceiling** (they need the user's and professor's decision):
  - cross-address caching (035 oracle ≈ 13×);
  - multithreading;
  - non-identical output: pruning features (L1-style sparsity is known to shrink CRFs with little accuracy loss), float32 weights, or retraining without expensive feature families. Accuracy could then be scored against the OSM sets' tag-derived ground truth (v3–v12 were assembled from labelled components). The user decided on 2026-10-04 that **output must stay byte-identical**, so this route is closed unless that changes.

## 8. Remaining ideas, ranked by honest odds (none promises 7.8×)

1. **More of 119's kind: precomputed feature ids for the remaining string-key families** (123: 17.5 keys/address).
   - **Bigrams (9.6/address) are the big one.**
   - New angle needed beyond 122/131: cache the canonical forms of the non-last part per token in the memo, then re-probe the cached share (needs ≥ 60%), then integer pair keys.
   - Alternative: a model-derived pair table keyed by (vocab slot, vocab slot) built from the bigram features that exist in the model. Check the memory (≈ 70 MB headroom; the 122 int-split already moved pairs and *saved* 48 MB peak, so memory may be available).
   - Expected: a few percent, more on OSM (compute).
2. **A pre-declared bundle of small, exact, positive-everywhere changes**: 133 (phrase-length join, +0.5/+0.9%, positive in every OSM round on two bases) + 130 (dictionary-phrase ids). Needs v12.
3. **Cache-friendly trie layout** (rebuild the double-array tries so children sit near parents) for the component and postcode tries: trie walks are the largest cold line item (≈ 0.28 µs). Exact; large engineering. Golden-v1-leaning risk (OSM trie costs are smaller).
4. **Direct row pointers** (store weight-row offsets instead of feature ids in dictionaries and id tables, removing the `indptr` hop). Exact; moderate effort. 137 suggests hot rows are cached anyway, so the expected gain is small.
5. **Reduce load time** (12 s → closer to 3 s) for the presentation: build the 056/101/119 tables offline into a sidecar file, or speed them up. No effect on the metric.
6. **Packaging** (required before the professor tests):
   - 091's backtrack must be guarded to aarch64;
   - remove the hard-coded paths in `build_cc.sh` (and the Homebrew mimalloc path);
   - one-command app: fetch the model, build original + ours, verify identical outputs, time both sequentially with rotation, report memory and threads, and emit JSON plus Markdown with setup and parse time separated.

## 11. Proposed rewrite track: how to break the incremental wall (PLAN ONLY, added 2026-10-04T18:55-0700)

**Status:** a proposal from a research conversation with the user. None of it has been built or measured. Estimates are labelled UNVERIFIED. It needs the user's explicit approval before any experiment starts, and §2's hard rules apply to it without exception.

### 11.1 Why the current loop has stalled (from the evidence above)

- The loop is **greedy hill climbing**: one patch at a time, accepted only if it is byte-identical *and* faster than the previous stack. That rule correctly blocks noise and overfitting, but it also kills every multi-step redesign at its first slower intermediate stage. 140 was stopped at its Phase 3 gate for exactly this reason.
- Recent yield: about 1–5% per accepted change, roughly 1 acceptance in 7 attempts (REACHABILITY_2026-10-03), and smaller on unseen data.
- §7: on OSM, 7.8× needs 2.48 µs against a ≈2.2 µs warm bound. **Memory-side work cannot reach it; per-address compute must shrink.**
- §5: the biggest recent win (119, +5.6% OSM) *removed compute* by replacing string keys with precomputed ids. That trend points at a front-half rewrite, not more micro-patches.
- Cold-µs targets in cpi (§4, development): context fill 1.75, features 1.40, accumulate 0.82, lookups 0.68. The paper floors for the first three are each far below today (LIMITS_2026-10-02 §3.7; these are limits, not predictions).

### 11.2 What published LLM-driven "breakthroughs" have in common

In none of these cases was the result produced by prompt wording alone. Every one comes from a **harness**:

1. **A near-perfect automatic verifier.** AlphaEvolve scores every generated program with automated evaluators. Anthropic's parallel-Claude C compiler: "the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." Bolzano (math) runs parallel provers against a separate verifier agent with a persistent knowledge base. **We already have this** (§2 rules, `tools/verify.sh`, unseen sets).
2. **A population, not a chain.** AlphaEvolve keeps every program and selects parents by fitness, so it can build on promising non-best programs. **We lack this.**
3. **Decompose a stuck problem with a partial oracle.** When 16 compiler agents all stalled on the Linux kernel, the author compiled most files with GCC and only the rest with the agents' compiler, so each failure pointed at one place. **We lack this at stage level.**
4. **New ideas come from outside the agent.** In the nanoGPT speedrun (Claude Code, about two weeks autonomous, set a record), agents "struggle to come up with new ideas on their own and need upstream human records"; a key idea arrived only after a restart re-fetched upstream repos. **We lack this**: experiments 001–140 came almost entirely from self-profiling.
5. **The harness handles stopping.** The same report logged Claude declaring "SESSION FINAL… exhausted" after 43 h and 46 h. The C-compiler harness instead restarts a fresh session in an outer loop, oriented by progress files. Encouragement in the prompt does not fix this.

Caveat: some headline math results were later disputed, and they tend to land where verification is cheap. Ours is cheap and exact. The one deviation from the published setups that is **required by our protocol**: timing cannot run in parallel on this laptop (§3, §6 "Parallel timing distorts results"). Building and correctness checks may run in parallel; benchmarks go through one serial queue.

### 11.3 The proposed harness (four parts)

1. **Stage-level oracles and hybrid builds.**
   - From the original library, dump per address: tokens, normalized strings, per-token feature-id lists (or keys), and per-token score vectors.
   - Each rewritten stage is behind an `EXP_*` flag (existing pattern) and must match its own oracle byte-for-byte on golden-v1, novel and OSM, **with every other stage the original code**. Only then is it combined.
   - The end-to-end §2 checks still gate every milestone.
2. **Milestone track with a small population.**
   - Declare the milestones and kill rules up front in a plan file (as for `INTERLEAVING_PLAN_2026-10-04.md`).
   - Correctness gates every step. **Speed is judged only at declared milestones** with the 121/103 protocol plus the unseen rule. Intermediate slowdowns are logged, not fatal.
   - Keep the top 2–3 variants alive (not just the best), each in its own experiment directory. Selection discipline from METHOD.md still applies.
3. **Idea injection (one session, no code).**
   - Collect outside techniques as one-page "idea cards", each aimed at a §4 stage. Candidate sources: fast CRF/sequence-labelling inference engines, compiling a linear model into code or tables, perfect/minimal hashing of feature keys, cache-oblivious or level-ordered trie layouts, SIMD tokenizers (simdjson-style classification), integer-only feature pipelines.
   - Each card states: mechanism, exactness obligation (no float-order change, §2.1), memory cost against ≈70 MB headroom, model-derived only (§2.5), and a cheap probe with a kill rule.
4. **Outer loop for long autonomous runs.**
   - A headless `claude -p` runner that starts a fresh session whenever one ends, oriented by a progress file (`research/plans/REWRITE_PROGRESS.md`), with the same rules as interactive sessions.
   - Parallel workers only for build and verification. A single serial timing queue gated by `tools/env_gate.sh` and the §3 hygiene checks.
   - Must work on macOS bash 3.2 (no GNU `timeout`).

### 11.4 Candidate first target and cost (UNVERIFIED)

- **Integer feature pipeline**: context fill + feature generation produce feature ids directly, with no string keys reaching the lookup. Generalises 119 to the remaining families (bigrams ≈ 9.6 keys/address, §8.1), and goes further than 122/131's failed bigram attempts by redesigning the stage rather than patching it.
- Size, gain and risk are UNVERIFIED. REACHABILITY_2026-10-02 estimated a front-half rewrite at weeks of work with exactness risk across tokenizer, normalization and feature generation. The stage oracles in 11.3.1 exist to contain that risk.
- **Cheap prerequisite (one session):** re-measure the warm bound and stage split on cpi (088's method). The REACHABILITY numbers are from pcp (≈5.1×). This tells whether any memory-side room remains and sizes the rewrite's ceiling before committing.
- **Deadline trade-off:** a well-documented 6× (ablation, confidence intervals, current professor-facing `README.md`) may be worth more than an unfinished rewrite. The user decides.
