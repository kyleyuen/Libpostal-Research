**Traps that cost time:**
- **Never run builds, checks or dumps while timing runs.** That contaminated 077's first screen.

- A prefetch wins only when it is issued a whole stage before a serialized dependent use, and the address comes from data already in hand (074, 077).

## 6. What does NOT work (do not retry without a new angle)

**Prefetch and latency hiding:**
- 004, 012 iC (second-level trie prefetch), 027 root cache, 037 lockstep walks, 046 early dictionary prefetch, 075 / 078 vocabulary-slot prefetch and eager memo fill, 081 push-time prefetch, 084 early postal-trie prefetch.
- 079 phrase-type prefetch: golden-v1 only.

- 044 / 046 / 050: lazy transition rows, interleaving.

**Layout and tables:**
- 030 / 015 pairs re-keying, 054 per-word vectors, 058 numeric postal table / checkpoint skip index, 063 address-dictionary first-token table, 066 re-zero only touched rows, 068 packed role rows, 087 dense rows (rows are 74/400 full), 092 skip-clear (15/20 rows touched).
- 031: denser or sparser dictionaries hit the memory rule.

**Compute:**
- 070 `-mcpu=native` / -O3, 018 tokenizer -O2, 097 unrolled accumulation, 072 backpointer no-clear.
- 016 T8 lean buffers, T7 word memo, prefilters (020: −2.5%).
- 071 **certified early exit**: label-path margins are 20–60× smaller than sound bounds; 0% of lookups skippable.

**Platform:** superpages are unavailable on macOS arm64. Parallel timing distorts results.

## 7. Ideas NOT yet tried (my ranking, with honest odds)

These are the things I would do next. Each states what it attacks, why it might work, and the risk.

**A. Precompute address-dictionary prefix/suffix results per vocabulary word.**
- *What it attacks:* context fill's address-dictionary search (0.27 cold / 0.06 warm) and prefix/suffix search (0.22 / 0.11).
- *Idea:* like 056's FTT, compute at load, from the model, for every vocabulary word its `search_address_dictionaries_prefix/suffix` result. Look them up via the vocabulary slot the context-fill slot loop already computes. Must be exact: the same function evaluated per word.
- *Expected:* about 0.2–0.4 µs cold (3–5% golden-v1), smaller on OSM.
- *Risk:* memory. Peak headroom is only about 70 MB (2.543 vs 2.613 GB). Store compactly: most words have no prefix/suffix, so use a bitmap plus a sparse side table. Read why 063 (address-dictionary first-token table) failed first; this is a different, simpler table.

**B. Merge the two normalizations per token (normal + admin) into one pass.**
- *What it attacks:* `normalize_token` (485 samples) and cstring copies. Today each token is normalized twice: the admin form shares the result only for ASCII without digits (`EXP_ADMIN_SHARE`).
- *Idea:* for tokens with digits, produce both forms in one scan (they differ only by DIGIT_CHAR replacement).
- *Expected:* about 1–2% warm. Exact and low risk.

**C. Remove strlen and memmove in feature building (finish what 067 started).**
- *Idea:* pass lengths through all `feature_array_add_nb` call sites, and through `cstring_array_add_string` / `cstring_array_get_phrase` where the length is already known.
- *Expected:* about 1–2% of warm time. Exact. Tedious, many call sites.

**D. Sparse-correction Viterbi that avoids clearing and loading the full score matrix.**
- *What it attacks:* score setup memset (857 samples, about 5.5% warm) plus the dense state-transition loads.
- *Idea:* about 26% of cells are touched per token. Compute the dense part from `prev[i] + trans[i][j]` (exactly equal in value to `(prev[i] + 0) + trans[i][j]` for untouched cells; only the sign of zero may differ, which the 091 argument already covers). Merge in the touched cells, computed exactly as `(prev[i] + st) + trans`. The per-column first-index tie rule must be preserved (merge in i-order, or keep a candidate index and compare carefully). Then the state-transition matrix needs no clearing, only touched-cell bookkeeping.
- *Expected:* about 3–5% warm (more on OSM).
- *Risk:* high complexity, and the exactness proof must be written out. Build a checker variant like 091's.

**E. Model-frequency-ordered data layout (hot/cold split).**
- *Idea:* reorder vocabulary-related structures (role rows, vocab slots/arena, weight rows of word features) so that frequent words, by the model's own vocab counts (allowed: model-derived), sit together. Fewer distinct pages and lines per address.
- *What it attacks:* first-touch cost (54% of golden-v1 time, 35% of OSM).
- *Expected:* unknown, possibly 3–8% on golden-v1. **Untested.**
- *Risk:* memory-neutral if it's only a permutation. Must not use benchmark statistics.

**F. Integer front half (the big one; needed for 7.8×).**
- *Idea:* intern each token once to a vocabulary id, generate all features as (name id, value id) integers, and give phrase strings ids via a model-derived phrase table. That removes the remaining about 30 string keys per address (hashing, strings, memmove/strlen) and most of feature generation's string work.
- *Expected:* this is the only path the 088 analysis says could approach 7.8× on OSM data.
- *Risk:* weeks of work and broad exactness risk.
- *Approach:* do it feature family by feature family, each behind a switch with an `_VERIFY` mode that builds both key forms and compares the looked-up ids. That is how 015 / `EXP_INT_KEYS_VERIFY` was done.

**G. Smaller:**
- (a) Skip `backward_edges` memset when 091's path is active. Trivial, but tiny.
- (b) Tokenizer (`scan_token` + `tokenize` about 0.14 µs warm): an ASCII-only fast tokenizer for the common case, checked against the re2c scanner. Moderate risk.
- (c) Response building (0.14 warm): build label strings without per-component mallocs.
- (d) Retrain PGO on a mixed development set (golden-v1 dev + a separate OSM dev set) for generality. Expect ≈0; low priority.

**Recommendation:**
1. Do A, B, C first (each exact, small, measurable).
2. Then D (biggest compute win with a contained blast radius).
3. Start F only if the user wants to commit days.
4. Run E as a cheap probe: measure distinct pages/lines per address with 045's `EXP_TRACE` before and after a permutation.
