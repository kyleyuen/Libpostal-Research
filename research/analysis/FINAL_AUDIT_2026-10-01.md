# Consolidated audit — libpostal parser speed research

Started 2026-10-01 PDT; cross-platform follow-up added later that day. Scope: the parser and its build path, benchmark harness, research protocol, numbered experiment records 000–028 (026 and 028 still in progress), packaged 021 sources, and the 025 audit builds. The pinned upstream checkout is `25099c506612b34b23b1bfe286ca6321fcf06f35`. This is an audit of the research objective, not a certification of unrelated libpostal APIs. The global engineering knowledge base had no matching project memory card; conclusions below come from repository and run evidence.

## Verdict

**The core parser optimization is implemented correctly for the tested contract.** The packaged 021 `l4` parses on one thread, gives byte-identical ordered components to the preserved original on golden-v1, the novel set, OSM and fuzz inputs, and uses less peak and steady footprint on this M4 Pro. Its controlled final-session speedups were **4.330×** on all 12,863 golden-v1 addresses, **4.358×** on 12,863 novel strings, **4.269×** on the non-ASCII floor, and **4.314×** on OSM. These are measured, same-session comparisons, above the 3.5× target. See [021](../experiments/021-final-stack/README.md) and the [professor report](../../README.md).

**The package has a confirmed optional API defect:** enabling feature printing aborts in the packed-weight fallback. Experiment [025](../experiments/025-audit-next/README.md) reproduces exit 134 and builds a repair whose output matches the original. Other teardown/save problems are source-level risks with narrower evidence. The repair is a separate maintenance candidate while 021 remains the accepted speed deliverable.

**No new speedup is established in 025.** A no-copy ASCII normalization candidate looked promising on short development runs, then showed 0.999× versus the repair on golden-v1 and 0.991× on novel in longer paired confirmation. It is rejected. All raw runs remain in 025.

## Cross-platform follow-up (026; in progress)

The [Linux ARM64 track](../experiments/026-cross-platform/linux/README.md) rebuilt the pinned original and exact 021 source inside Docker Desktop's Linux VM on the M4 Pro. Ordered output matches on golden-v1, novel and OSM; the candidate was observed on one thread. The exact 021 dictionary settings **fail** the Linux memory rule: peak RSS 2,347,384,832 bytes with glibc, versus 1,960,681,472 for the original; mimalloc 2.1.2 and 3.5.3 used still more. A separate candidate that removes only `EXP_LOADF=4` remained byte-identical and used about 14–15 MB less peak and late RSS than the original in paired golden-v1, novel and OSM runs. Its controlled speed checks remain pending; it is not yet a Linux speed deliverable. Setup on Linux golden-v1 rose to about 10.1 s from 2.46 s. Separately, x86-64 Linux ELF builds with upstream SSE2 flags were run under emulation and matched original output on all three sets; this is functional evidence, **not x86 speed or memory**. Mac footprint and Linux RSS are different metrics and must not be numerically compared.

A Linux ARM64 diagnostic stopped safely after nine golden-v1 runs and before novel timing when the laptop had to close. Dense/original paired warm speedups were 3.5455/3.5225/3.1939× (median 3.5225×). The host was heavily contended, only 1 of 447 original warm passes met the clean-pass rule, and its first pass was prewarmed with another input set. The result is **not an accepted Linux 3.5× claim**: a quiet same-session comparison, novel set, and true no-warmup cold check remain necessary. Further timing was paused when the laptop went off AC.

The [Windows x64 track](../experiments/026-cross-platform/windows/README.md) cross-built the pinned original and a Windows-adapted 021 candidate as PE DLLs with paired output and benchmark programs. Review found and corrected two sparse-arena allocation defects, preserving every attempt; the final compile-only package is `l4_r3`. The user has no Windows machine or VM, so **no Windows binary was run**. Windows output, thread count, memory and speed remain unverified, and the 025 feature-print repair is not in this binary. The [actual 021 Mac profile](../experiments/026-cross-platform/profile/README.md) identified phrase trie search as the largest named hotspot. [027](../experiments/027-root-transition/README.md) tested an exact root-transition cache: full output checks passed, but five paired development runs showed 0.998× candidate/control under host noise. It is rejected as a speed change, with no new gain established.

The [upstream README](https://github.com/openvenues/libpostal/blob/master/README.md) says to disable SSE2 on an M1 for a build that may perform worse. That is an architecture-specific instruction, not evidence that Linux or Windows is faster. The pinned [configure source](../../libpostal/configure.ac) already excludes SSE2 flags on `arm64`/`aarch64`; the Windows x64 configure enables them. The measured 4.33× is a same-Mac comparison of original and optimized builds, and cannot be transferred to another CPU or operating system by reasoning from this flag.

## Source findings, ranked

1. **Confirmed crash in a supported feature-print mode (high).** `crf_tagger_score` in the 021 packed-row build reaches an unconditional `abort()` when `print_features` is true or dictionaries are disabled ([021 `crf.c`](../final/021-l4/sources/crf.c)). The 025 API probe returns 134. The 025 patch applies packed row records to both fallback scoring routes; the feature-print probe returns 0 and its output matches the original byte for byte. A full golden-v1 run with feature dictionaries disabled also matches the original. Evidence: [025 raw commands](../experiments/025-audit-next/raw/commands/).
2. **Potential reload memory error and stale model state (high, source-level).** `crf_lean_cap_items` is static, tied to the old context, and is not reset by 021 `crf_destroy`. After teardown a new context can have smaller matrices while the global capacity still suppresses resizing; subsequent `memset` or scoring can exceed their allocations. Integer-key and role-ID globals also survive, with leak/staleness risk. 025 resets/frees them. Its teardown/re-setup probe matches the original, but a targeted sanitiser run designed to force the bad capacity was not done. Do not present this as a dynamically reproduced crash.
3. **Partial-allocation recovery and teardown ownership (medium, source-level).** 021 `rs_ready` returns true whenever `rs_tokens` exists, even if a later scratch allocation failed. The scratch objects also survive parser teardown. 025 allocates missing pieces independently and frees them at teardown, detaching the borrowed `rs_ts->str` pointer before destruction. Normal and lifecycle output checks pass; induced allocation failure was not tested.
4. **Optimized model cannot be saved with the old serializer (medium, source-level).** 021 converts/frees feature tries and packed CSR index arrays, while `crf_save` still assumes they exist. 025 returns false before opening an output file when these structures are absent. It prevents a likely null dereference but does not implement serialization of the optimized format. No save round-trip is claimed.
5. **The portability and packaging gap matters to the professor (high delivery risk).** The measured `l4` build includes ARM NEON, local PGO training, tokenizer flags, and mimalloc for its Mac memory result; its build instructions have local absolute paths. The exact 3.5×/memory combination on the professor's machine has not been verified. The [022 portable Mac build](../experiments/022-portable-floor/README.md) is fast but fails memory; [023](../experiments/023-memory-diagnosis/README.md) traces the extra retained pages to load-time temporaries, and [024](../experiments/024-release-freed/README.md) shows allocator pressure relief did not fix it. Linux ARM64 026 confirms that the exact 021 sparse-table settings also fail memory there, while a denser variant passes repeated novel-set memory checks with controlled speed still pending.
6. **Unrelated upstream varargs bug (low for this parser experiment).** The compiler warns that `address_phrase_in_dictionaries` reads a variadic argument with `va_arg(args, uint16_t)` even though `uint16_t` is promoted to `int` ([upstream source](../../libpostal/src/address_dictionary.c)). That is undefined behavior if called. A source search found no call site in this checkout, so it does not explain any measured parse result. The pinned upstream tree was not edited for this research fix.

## What the experiments actually show

- **Main causal gains:** exact model-derived feature and vocabulary dictionaries (006/010), direct key construction and integer keys (009/015), normalization paths proven against the transliteration rules (011/016), object reuse and packed rows (019), then load factors, constant feature IDs and mimalloc (020/021). Each accepted step has output checks and a same-session baseline or incremental control in its record. Compiler choices are part of the implementation, not a free claim about the C algorithm on every platform.
- **Failures were retained:** interleaved trie prefetch (004), several inline/Viterbi/phrase-prefetch changes (012), three 016 substeps, GCC/clang 23 and phrase prefilters in 020, the portable memory experiment (022), allocator pressure relief (024), and ASCII borrowing (025). These argue against promising a gain from an idea alone.
- **Measurement records:** 000/002 establish baseline and variability; 001/008/014 profile and model analysis; 007 checks environment/rebaseline; 013 measures random subsets and a non-ASCII floor; 017/018 and 019–021 refine the accepted build. The [ledger](../experiments/README.md) links every record, including the previously missing 008 row.
- **Correct the old prose:** [the 2026-09-30 source audit](AUDIT_REPORT.md) calls the 2.33× non-ASCII result a “guarantee” for unseen inputs. It is a **measured floor on that particular subset**, not a lower bound on arbitrary future data. Its 66 optimization ideas and percentage estimates are hypotheses from an older build (`h`), not measured remaining gains in `l4`. The same document treats the synthetic novel set too strongly in places; use the dataset limits above.

## Where further speed is plausible

The current 021 stack has removed many obvious costs. The [actual 021 profile](../experiments/026-cross-platform/profile/README.md), sampled separately from timing, found phrase trie search at 16.7% exclusive and CRF dictionary lookup at 10.9%; inlined work remains partly opaque. [027](../experiments/027-root-transition/README.md) found that an exact root-transition cache did not improve development speed. The next code-derived options are:

1. Examine CRF dictionary key construction and probing, which the 021 profile still shows as material. A fused key/hash path might avoid rescanning, but earlier inline lookup variants failed; use a new paired test, not the old estimated percentages.
2. Co-locate feature dictionary entries with their packed weight rows so a successful lookup needs fewer independent reads. This changes model-load layout and peak memory, and needs byte-identical scoring order plus full peak/steady checks. The old audit's 5–8% estimate is **unverified and stale**, and LTO obscures part of scoring in the current profile.
3. For cross-machine delivery, build integer/string tables directly from model tries so temporary full dictionaries are never allocated. This targets 022's portable-memory failure, not an asserted speed gain. It has higher delivery value if the professor uses a different allocator or architecture.

The rejected 025 borrowing variant should not be folded into the final build. Do not add the old audit's individual gain estimates or describe random-subset results as guarantees. The next accepted speed result requires the same corpus, original baseline, output, thread, cold, memory, and environment gates in [METHOD.md](../METHOD.md).
