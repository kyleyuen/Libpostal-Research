# How fast could this parser architecture possibly run? A lower-bound analysis (paper only)

Date: 2026-10-02. Author: analysis subagent, for the main research session. **Nothing was built, run, timed or loaded for this document.** It uses existing measurements, the `l4` source code and arithmetic. Every number is tagged:

- **MEASURED**: from a file in this workspace (path given).
- **DERIVED**: computed here; the formula and its inputs are shown.
- **ASSUMPTION / UNVERIFIED**: not backed by a measurement on this machine.

None of the floors below is a predicted speedup. They are limits that no exact implementation can beat under the stated model. Real code will sit well above them.

## 2. The model of a floor

For each stage, three separate limits are counted:

- **Compute floor** = the minimum instructions the stage must execute ÷ (issue width × clock). Viterbi is limited by SIMD pipes instead (instructions ÷ 4 pipes).
- **Memory throughput floor** (Little's law, `ALGORITHM_RESEARCH.md` §6.5) = N · λ / M, where N is the number of cache lines that miss. Because M = 29.7 is a lower bound on parallelism, this floor is an **over**-estimate of the true floor.
- **Dependent-chain floor** = D · λ, where D is the number of misses that must happen one after another. For a feature: vocabulary entry → feature key slot → (in `l4`) offset → weight row.

Libpostal's API parses **one address per call**, so this chain cannot be hidden behind another address's work. A batched API could hide it (§4c).

Bounds:

- **lower bound** = max(compute, N·λ/M, D·λ), which assumes perfect overlap;
- **pessimistic floor** = compute + N·λ/M + D·λ, which assumes no overlap between the three.

Warm vs cold: today's cold first pass (7.90 µs) is barely slower than warm (7.83 µs), because instruction overhead dominates. **That will not hold near the floor**, where memory dominates. So both an all-cold N (distinct lines per address) and a warm N (LRU-model misses) are shown.

## 3. Bottom-up floor per stage

Instruction counts are DERIVED from the source structure (`final/021-l4/sources/`) and the measured workload. The per-item costs (for example "~20 instructions to form and hash an integer feature key") are **ASSUMPTIONS** of what tight code needs. They are given so anyone can redo the sum.

### 3.1 Normalize and tokenize (MEASURED today: 0.066 + 0.222 µs)

Minimum work is a scan of 39 bytes:

- normalization: about 2 instructions per byte, about 80 instructions (ASCII);
- tokenizer DFA: about 4 instructions per byte plus about 10 per token, about 215 instructions.

The DFA step is a dependent chain from one byte to the next, but it stays in L1. 39 bytes × 1–4 cycles is 39–156 cycles, so the **floor is about 0.01–0.035 µs (compute/latency-bound)**.

Exactness obligation: the token *types* must match re2c's (`ALGORITHM_RESEARCH.md` A8). Non-ASCII input costs more. The 016 floor set measured normalize at 0.156 µs (`experiments/016-batch/raw/batch/C-stages-summary.md`).

### 3.2 Context fill (MEASURED today: 2.179 µs)

The work is greedy longest-match phrase search over three tries:

- address dictionary, 8.7 MB file;
- parser phrases, 137 MB;
- postal codes plus graph, 622 MB.

There is also a prefix/suffix search per token, and admin normalization.

Minimum work with the **same algorithm** (case a): roughly 5.9 token starts × 3 tries, plus 2 × 5.9 prefix/suffix searches, gives about 30 walks. At most about 150 byte transitions in total, bounded by about 39 bytes per trie. At about 6 instructions per transition plus bookkeeping, that is **about 1,100 instructions, about 0.03 µs** at 8 IPC (DERIVED).

**Memory: not measured.** The number of cold trie nodes per address is unknown, because Q3 excluded the tries.

- ASSUMPTION: 10–40 cold lines per address (basis: about 3 phrase matches per address, `phrase` features 32,103/10,305 in `014/data/q6.md`, with about one cold line per matched byte beyond the hot top levels).
- That gives 0.04–0.17 µs at M = 29.7. However, each walk is a dependent chain as long as its phrase, so the real overlap is lower.

With **exact algorithm changes** (case b), a hashed lookup of candidate token spans can replace the trie walks. It needs about 600 instructions and has independent misses. Exactness obligation: it must reproduce `trie_search_tokens_from_index`'s longest-match and restart state machine exactly (Lemma 3 / Q7 caveats in 014).

**Floor: about 0.05–0.2 µs, low confidence.**

Caution from evidence: the first-byte walk is **not** where today's 2.2 µs goes. Experiment 027 (root-transition cache) measured 0.998×, and 016 T6 / 021 `s4` (two-byte prefilter) measured no gain. The gap is somewhere else in context fill (admin normalization, phrase-membership arrays, string handling). It needs the instruction-level split before it can be attacked.

### 3.3 Feature generation (MEASURED today: 2.027 µs)

The minimum output is 54.6 feature ids per address.

- **Case a (l4's algorithm):** about 76% of lookups already use integer keys (Q6 reach R = 0.762, `014/data/q6.md`). About 24% still build strings (22.6-byte keys, 002 §2). The estimate is 54.6 × 20 + 0.24 × 54.6 × 22.6 × 1.5 ≈ **1,540 instructions ≈ 0.04 µs**.
- **Case b (interned ids everywhere, including phrase ids from the phrase match):** about 54.6 × 12 ≈ **660 instructions ≈ 0.02 µs**.

Branch mispredictions are not in the floor. ASSUMPTION: about 10 data-dependent branches per token, 20% mispredicted, about 15 cycles each, adds about 0.04 µs.

Vocabulary misses are counted under lookups. **Floor: about 0.02–0.08 µs (compute-bound).**

### 3.4 Lookups and accumulation, as one block (MEASURED today: 1.146 + 1.093 = 2.239 µs)

**Compute.**

- Probing: 54.6 × about 12 instructions, plus 5.9 vocabulary probes × 20, about 770 instructions.
- Accumulation: the number of weight entries per row was **never measured**. ASSUMPTION: 9–16 entries per state row, giving about 420–750 additions per address. This is inferred from Q3's 58 `indices` and 89.5 `data` distinct lines over about 47 hits, using E[lines] = 1 + (bytes − 8)/128. The two inferences disagree, so the range is wide. Transition rows are unknown.
- At about 4 instructions per entry (load the packed record, then load, add and store the label), that is about 2,400 instructions.
- The label-by-label summation order must stay the emission order (Lemma 1, `ALGORITHM_RESEARCH.md` §6.2). Each label's partial sum is a chain through memory: store-to-load forward plus FADD, about 8 cycles (ASSUMPTION). Tokens are independent and can overlap.
- **Compute: about 3,200 instructions ≈ 0.09 µs.**

**Memory: layout `h`, MEASURED (014 `data/q3.md`).**

- 270 distinct 128-B lines per address: slot 55, arena 44, indptr 23.5, indices 58, data 89.5.
- Exact-LRU misses of this stream alone: 76.4 per address at 16 MiB, 57.8 at 64 MiB.

**Memory: layout `l4`, DERIVED, not measured.** The estimate is slots 55 + arena 44 × (1 − 0.762) + indptr 23.5 + packed 10-byte rows ≈ 89.5 × 10/8 ≈ **201 distinct lines** (indices merged away). It assumes:

- integer-keyed lookups need no arena line;
- load factor 0.25 keeps hits at one slot line;
- packing replaces the two arrays with 1.25 × the data lines.

The warm estimate is 76.4 × 201/270 ≈ **57 misses** (ASSUMPTION: misses scale with distinct lines).

**Memory: case b, ideal layout, DERIVED.**

- The key check and the weight row share a record. A perfect hash or one-probe table gives one line per lookup, plus a second line for long rows, so about 1.7 lines × 54.6 + about 6 vocabulary lines + about 10–20 phrase lines ≈ **115 distinct lines**. Warm: 76.4 × 115/270 ≈ **33 misses**.
- Exactness obligation: even a minimal perfect hash needs a full key check, because about 16% of state lookups and about 5% of transition lookups miss.

**Resulting floors at M = 29.7 (N·λ/M):**

| Layout | N warm | N cold | N·λ/M warm | N·λ/M cold |
|---|---:|---:|---:|---:|
| `l4` (case a) | 57 | 201 | 0.24 µs | 0.86 µs |
| ideal (case b) | 33 | 115 | 0.14 µs | 0.49 µs |

**Dependent chain (D·λ) when cold:**

- `l4`: vocabulary → slot → indptr → row, D = 4, so 0.51 µs;
- case b: vocabulary → co-located record, D = 2, so 0.25 µs.

**This block is memory-bound, not compute-bound.** Its floor is about 0.14–0.86 µs, depending on layout and warmth.

Per-word precomputed partial scores (`ALGORITHM_RESEARCH.md` §3.1) are a small extra. They are exact only for the 24.8% of plain tokens where the unary block is a prefix (Q5, `014/data/q5.md`). They must also fit in about 143 MB: 250k words × 160 B ≈ 40 MB fits; the full vocabulary, about 590 MB, does not.

### 3.5 Viterbi and the rest of predict (MEASURED today: 1.004 µs, combined)

**Viterbi** (`crf_context.c:570`, NEON path, two labels per vector):

- (T−1) × L × L/2 = 4.878 × 20 × 10 = 976 vector steps.
- Each step is 2 FADD, 1 compare and 2 selects (5 SIMD operations) plus 2 loads.
- 4,878 SIMD operations ÷ 4 pipes = 1,220 cycles, so **0.27 µs** (DERIVED; 4 pipes UNVERIFIED).
- Case b: compute the value with `fmax` and recover the index afterwards. That is about 3 SIMD operations per step, about **0.16 µs**.
- Exactness obligation: it must keep the "first i with strictly greater score" tie-break and the signed-zero/`max < score` semantics.
- The fold `(prev[i] + st[t][i][j]) + trans[i][j]` must not be reassociated (Lemma 1).

**Rest of predict:** today `l4` clears the T × L × L state-transition matrix, about 4.88 × 3,200 B ≈ 15.6 KB, about 490 store-pair instructions, about 0.03 µs.

- Case b: rows with no transition feature could point to one shared zero row. Viterbi reads the same zeros, so this is exact, and the cost is about 0.

**Floor: about 0.16–0.30 µs (SIMD-bound).** This is the only stage whose floor is set by arithmetic that cannot be removed.

### 3.6 Response (MEASURED today: 0.194 µs)

Copy about 39 bytes and the labels into one block (`ap_response_block`). About 300 instructions, so **floor ≈ 0.01 µs**.

## 4. Theoretical maximum speedup vs the original (33.92 µs)

These are **limits, not predictions**.

**(a) Same algorithms, perfect implementation** (`l4`'s data structures, ideal instruction stream).

- Lower bound = max(compute 0.46, memory 0.24–0.86, cold chain 0.51) ≈ **0.5 µs**.
- Pessimistic = 0.46 + 0.86 + 0.51 + trie memory (0.05–0.17) ≈ **1.9 µs**.
- **Ceiling about 18× to about 68×.**

**(b) Exact algorithmic changes allowed** (all of these within ~143 MB of headroom, with the exactness obligations above):

- integer keys everywhere;
- co-located key and weight records with one-probe or perfect hashing;
- hashed phrase lookup;
- shared zero rows;
- `fmax` Viterbi;
- partial per-word scores.

- Lower bound = max(0.30, 0.14–0.49, 0.25) ≈ **0.30 µs**.
- Pessimistic = 0.30 + 0.49 + 0.25 ≈ **1.05 µs**.
- **Ceiling about 32× to about 113×.**

**(c) Only if a constraint is broken** (forbidden or out of scope):

| Change | Rule broken | Rough extra effect |
|---|---|---|
| Parse addresses on several cores | single thread | up to ×8 throughput on the 8 P-cores (MEASURED core count). Scaling is ASSUMPTION; bandwidth is not binding: about 35 KB/address per core is far below the M4 Pro's published bandwidth (ASSUMPTION) |
| Cross-address result cache, or a vocabulary/feature memo kept between calls | no memoization across addresses | a replayed benchmark degenerates to one hash plus one lookup, about 0.05 µs. Invalid by design |
| Reassociated or float32 sums; dense per-word scores for all tokens (incl. the 64% that start with postcode features); SIMD reductions | byte-identical output | accumulate and part of lookup could almost vanish (≲ 1 µs today, ≲ 0.1 µs at the floor). It could become legal only through the certified-argmax-with-exact-fallback route (`ALGORITHM_RESEARCH.md` §6.3), which is unbuilt research |
| Full 3.69 M-word partial-score table (~590 MB) | peak memory | removes about one lookup per plain token; exceeds headroom by about 450 MB |
| Batched / software-pipelined multi-address API (single-threaded, no memo) | none of the stated rules, but the professor times his own per-call harness | hides the D·λ chain (0.25–0.51 µs cold) and lets M approach its limit across addresses |

**Interpretation.** `l4` at 7.83 µs is about 7.5–26× above the case-(b) band (7.83/1.05 to 7.83/0.30; corrected per §8) and about 4–16× above case (a). The program is limited **neither by memory nor by arithmetic**, but by the number of instructions and stalls its generic, branchy, string-oriented code executes. This matches Chen & Manning's observation that feature computation dominates this class of parser (`ALGORITHM_RESEARCH.md` §1).

## 5. Sensitivity (the headline must not hinge on 8 IPC)

Floor in µs = compute(IPC) + N·λ/M (cold N) + D·λ. This is the pessimistic additive form; Viterbi is held on 4 SIMD pipes.

| IPC | M | case a (N = 201, D = 4) | speedup vs 33.92 | case b (N = 115, D = 2) | speedup |
|---:|---:|---:|---:|---:|---:|
| 8 | 29.7 | 0.46 + 0.86 + 0.51 = 1.83 | 18.5× | 0.30 + 0.49 + 0.25 = 1.04 | 32.6× |
| 4 | 16 | 0.65 + 1.60 + 0.51 = 2.76 | 12.3× | 0.44 + 0.91 + 0.25 = 1.60 | 21.2× |
| 2 | 8 | 1.03 + 3.20 + 0.51 = 4.74 | 7.2× | 0.72 + 1.83 + 0.25 = 2.80 | 12.1× |

Even the most pessimistic row (IPC 2, M 8, every address cold, with chains fully serialised) leaves the floor at ≥ 7× vs the original, against 4.33× achieved. With warm N (57 / 33), the memory terms shrink 3.5×.

**Practical expectation (ASSUMPTION, not a prediction):** real optimised code typically lands at a few times its floor, so something like 2–4 µs (8–17×) is plausibly the region where further exact engineering stops paying. No experiment supports any number above 4.33×.

## 6. Headroom ranking

1. **Context fill, about 2.1 µs gap, lowest confidence.** It is the largest stage, but its floor depends on unmeasured trie-node misses. Two direct attacks on the first-byte walk measured nothing (027 0.998×, 021 `s4`), so the cost lies in work around the walks.
2. **Feature generation, about 2.0 µs gap, high confidence that the floor is tiny.** The floor is compute-only and very small, so nearly all 2.0 µs is overhead: string building for about 24% of keys, branching, copying (`memmove`/`strlen` are 9% of `l4` samples, 026 profile).
3. **Lookups + accumulate, about 1.7–2.0 µs gap, medium confidence.** The floor is memory-bound. The levers are fewer lines per lookup (co-location, no indptr hop) and shorter dependent chains.
4. **Viterbi + rest, about 0.7–0.85 µs gap.** It is the closest to a hard floor that cannot be removed (SIMD arithmetic about 0.16–0.27 µs). The rest is matrix clearing and setup.
5. **Tokenize / response / normalize, about 0.4 µs combined.** Normalize is already near its floor (0.066 µs vs about 0.01 µs). Tokenize and response each have about 0.2 µs of overhead.

**No stage is at its floor.** Viterbi's arithmetic and ASCII normalization are the closest.

## 7. Confidence and how to tighten the bound

**Biggest uncertainties, in order:**

1. Trie-walk memory traffic in context fill: unmeasured.
2. Weight entries per row/address: unmeasured; the inferred range of 9–16 disagrees with itself.
3. `l4`-layout line counts: DERIVED from the `h`-layout trace by scaling.
4. Core widths and clock: UNVERIFIED.
5. M = 29.7 is only a lower bound, so the memory floors may be lower still.
6. 029 stage µs come from a timer build and are preliminary.

**Single most useful measurement: the 029 instruction and cycle counts, already running.** To plug them in:

- `IPC_l4` = I_l4 ÷ C_l4, from (22-pass − 2-pass)/(20 × 10,308) for both instructions and cycles.
- **Instruction gap** = I_l4 ÷ I_min, with I_min ≈ 13,700 for case a and 8,400 for case b (§3.7).
- How to read IPC_l4:
  - if it is about 1 or below, `l4` is stall-bound: the memory and chain floors (§3.4) are what to beat, and line-count reductions are the lever;
  - if it is about 3 or above, instruction count is the lever: string building, branches and copying in features and context fill.
- The original's I and C give a machine-independent "removed work" ratio I_orig ÷ I_l4. Compare it with 4.33×.
- Replace the §1 table with 029's final medians once its owner publishes them, and recompute the "Gap" column.

**DERIVED from these counts:**

1. **Where the 4.33× came from.** `l4` executes 2.90× fewer instructions (210,803 / 72,591). Its cycles fall 4.31× (138,854 / 32,219), which matches the timed 4.33×. The remaining factor of 4.31 / 2.90 = 1.49× comes from higher IPC: fewer stalls per instruction, from the memory-layout and prefetch work.
2. **Effective clock.** 32,219 cycles ÷ 7.83 µs (021 timing) ≈ 4.11 GHz, and 138,854 ÷ 33.92 µs ≈ 4.09 GHz. That is below the 4.51 GHz ASSUMPTION in §0. 3. **Instruction gap.** I_l4 ÷ I_min = 72,591 / 13,700 ≈ **5.3×** for case a, and 72,591 / 8,400 ≈ **8.6×** for case b. So about 59,000–64,000 of the 72,591 instructions per address are not required by the work itself.
4. **Cycle gap.** 32,219 cycles against a compute floor of about 1,360–2,080 cycles is a **15–24× gap**. At 2.25 IPC, `l4` is not mainly stall-bound, which is the §7 reading "between 1 and 3 → both levers". Most of its cycles are spent issuing instructions it does not strictly need. Cutting instruction count, in features and context fill above all, is the larger lever. Memory-line reductions matter mainly for the lookup and accumulate block.
5. **Back-of-envelope cap on instruction-count work alone (ASSUMPTION: IPC held at 2.25).**
   - Reaching I_min would give 8,400–13,700 / 2.25 ≈ 3,700–6,100 cycles, about 0.9–1.5 µs.
   - That is about 23–38×, provided the memory floors (§3.4) overlap.
   - At a realistic 2× above I_min, it is about 1.8–3.0 µs, roughly 11–19×.
   - This is consistent with the §5 "practical" band. It is not a prediction.
