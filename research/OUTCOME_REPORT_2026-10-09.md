# Libpostal optimization outcome report

**Status:** final AC timing and peak calculations cover 14 datasets and 130,341 rows. All 84 timing captures exited successfully, and every parsing-duration gate passed (minimum 10.791333 seconds). The source-weighted warm-parsing geomean speedup is 5.893289×; the unweighted 14-set warm-parsing geomean is 5.806217×. Source geomeans are 5.782694× for `openstreetmap` (12 datasets), 6.033570× for `senzing` (golden-v1), and 5.866359× for `senzing-style` (novel); the weighted result gives the three source labels equal weight. Global maximum peak is 2,543,405,432 B for CPI versus 2,613,905,616 B for original, a 70,500,184 B reduction. The Senzing pair still has a +58,982,640 B peak regression; v14 peak is 94,027,608 B lower. OSM load varied substantially. Thread samples on golden-v1, osm-v3, and v14 each observed one thread; the direct v14 supplement used six live samples per role. The [final independent audit](experiments/202-cpi-final-validation/raw/final-independent-audit-v1.md) records the rollup and evidence identities. Earlier stopped and battery-power attempts remain separately documented. This report does not claim that the current package is globally optimal.

## Goal and acceptance rules

The project seeks faster default address parsing while retaining ordered labels and components, using one parser thread, and staying within the original build’s peak and steady memory. The required correctness gate is byte-identical parser output against the preserved original on the declared input sets. Passing a finite set of addresses does not prove behavior for every possible address or public API state. The detailed protocol is in [METHOD.md](METHOD.md).

## Accepted package and implementation

The accepted package is `cpi`, recorded in [the 119 build record](final/119-cpi/BUILD.md). Experiment 119 adds a model-derived component-phrase ID table over the earlier 114 package; it inherits earlier work, so the whole package should not be attributed to experiment 119 alone.

The enabled paths use dictionaries and integer feature IDs, per-address reuse for vocabulary and word work, model-derived phrase and postcode tables, length-aware string operations and normalization fast paths, and a Viterbi specialization for the 20 labels. On supported Apple Silicon builds, the Viterbi path also uses NEON instructions within the parsing thread. The NEON source is architecture-guarded; this is not multithreaded parsing. Exact switches and source identities are recorded in [switches.txt](final/119-cpi/switches.txt) and [build_hashes.txt](final/119-cpi/build_hashes.txt). The build used Apple Clang, O2, link-time optimization, profile-guided optimization trained on golden-v1 development data, scanner O1, and mimalloc. These are package-level facts; the available measurements do not isolate each feature’s speed contribution.

## Experiment 201: token-span candidate

Experiment 201 compared candidate 199’s token-span views with a source-matched CPI control. It was not promoted. In all-13 diagnostic captures, both variants matched output bytes and had one parser thread. Candidate counters recorded 616,106 token views covering 3,531,981 referenced payload bytes and 72,711 fallback token copies (287,019 bytes); the CPI control copied 688,817 retained tokens (3,819,000 bytes). These are token payload operation counts, not a claim of zero-copy parsing or end-to-end allocation reduction. The instrumentation did not cover every allocation site.

The bounded, uninstrumented timing screen used 12,863 golden-v1 rows, three rounds and 200 passes per round. Warm medians were 5.558 µs/address for 199, 5.604 for matched CPI, and 5.286 for packaged CPI. This small one-corpus screen was inconclusive under variable system load and does not establish a speed benefit. Peak footprint was 2,537,359,736 B for 199, 2,537,343,352 B for matched CPI, and 2,612,709,584 B for original 000. Steady results were rounded to MB, so they cannot establish a strict byte-level memory gate. Native API memory captures also put candidate maximum 16,408 B above matched CPI; these whole-process captures varied and do not settle the memory comparison. The full source, counters, limitations and preserved failures are in [the 201 report](experiments/201-cpi-work-and-memory-prep/REPORT.md).

## Exploratory candidates

Experiments 198–200 explored certified decoding, token spans, and a fused ASCII front end. None is promoted over CPI. The 198 certifier used an exact fallback when it could not certify the path and passed its finite screens, but it added a quadratic certificate-bound scan and finite coverage cannot prove universal correctness. Experiment 200’s whitelist accepted only 24 of 12,863 golden rows in its diagnostic screen and incurred extra fallback work, so it was stopped. Experiment 199’s measurable copy reduction did not translate into a conclusive speed or memory improvement over accepted CPI. The individual records and failed attempts remain in the [architecture exploration report](analysis/parallel-exploration-2026-10-07/REPORT.md).

Earlier redesign results show why structural wins alone are not enough. Experiment 181 was output-identical and single-threaded, but experiment 183 measured 1.15× the original on golden-v1, 1.13× source-weighted over all 13 datasets, and 1.08× unweighted over all 13, with peak footprint 1,720,320 B above original; it was rejected. CPI measured 5.70× overall in that historical comparison, with peak footprint 69,992,304 B below original. Experiments 184–187 established operation and source-trace evidence but did not run a final speed campaign; 185 recorded 39/39 output-identical records, while 186–187 documented coverage and repeat-consumer limits. Experiments 188–196 were structural development/golden screens or diagnostics without final speed and memory promotion evidence; some proposed reuse overlaps behavior already present in CPI. Combined candidate 197 passed its declared all-13 output/thread, fuzz and safe-API checks and reduced counted search calls relative to 181, but had no speed result, rounded-equal steady footprint and API peak above original, so it was not promoted. See the [experiment ledger](experiments/README.md), [183 record](experiments/183-full-architecture-benchmark/README.md), and [197 record](experiments/197-combined-query-removal/README.md).

## Evidence scope and remaining limits

- The 202 output stage byte-compared serialized files for 14 datasets and 130,341 addresses. This finite corpus does not prove behavior for arbitrary inputs or API states.
- The 202 all-13 fuzz check compared SHA-256 digest/status streams with frozen original references; it did not compare each serialized output byte or rerun the original pipeline. Experiment 202 ran no fresh native API suite, exact-serializer fuzz suite, or v14-specific fuzz suite.
- Thread samples on golden-v1, osm-v3, and v14 observed one thread. The full-suite peak maximum is below original, while the Senzing subgroup independently exceeds its peak limit. The public feature-print API is a known failure: the experiment 150 CPI probe aborted (exit 134) while original exited 0. The 78 selected safe API cases in experiment 201 do not establish complete API parity. Output comparison covers the declared finite inputs, not every possible address or API state.
- The package build facts establish enabled code and build settings, not the independent effect of each optimization. Platform portability and public API coverage have separate limits recorded in the package and experiment reports.

Separate prior API evidence from experiment 201: the accepted-CPI archive (`e56d3ae4…`) with canonical mimalloc (`03460b36…`) passed 78 selected ordered-output rows byte-identically against original, with one sampled thread and exit 0. The harness used a shared-library adaptation linked from the accepted 119 archive; it was not the packaged executable and did not cover every API state. Experiment 150 also records that the public feature-print API exited 134 (abort) in CPI while the original probe exited 0. Therefore, the accepted default parser output does not establish full public API parity. The separate 200,000-case exact-serializer fuzz capture was for candidate 199’s archive, not accepted CPI, so it is not evidence for the current package. See the [201 report](experiments/201-cpi-work-and-memory-prep/REPORT.md) and [150 audit](experiments/150-independent-professor-audit/README.md) for scope and supporting evidence.
